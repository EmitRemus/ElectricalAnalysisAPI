# Electrical Dataset v1

Проєкт контракту для POST /v1/datasets. JSON Schema Draft 2020-12 задає схему записів, а openapi.json описує HTTP. Усі приклади демонстраційні.

## Завантаження

JSON передає один об’єкт dataset із непорожнім масивом records. NDJSON у UTF-8 починається одним об’єктом header із record_type = dataset. Далі кожний рядок містить один record. Допускаються LF, CRLF і кінцевий перенос рядка. Усередині потоку порожній рядок є помилкою. Схеми header, record, dataset перевіряються за відповідними посиланнями #/$defs/… згідно з позицією запису. Загальна коренева схема описує всі три форми. Повторювані ключі JSON та нечислові значення NaN/Infinity відхиляються. Необов’язкові поля можна пропускати. Явний null не допускається.

## Відображення у Parquet

Кожен dataset_id має окремий простір таблиць. Одна таблиця може складатися з декількох частин Parquet. Колонки відповідають іменам полів запису. record_type визначає таблицю. Час зберігається як timestamp[us, UTC], числа як float64, цілі як int64, прапорці як boolean, текст як UTF-8. Відсутні необов’язкові поля дають null у таблиці. Схема таблиці фіксується до першої порції. Заголовок зберігається як метадані набору.

| Тип запису | Таблиця | Колонки (знак ? означає необов’язкове поле) |
|---|---|---|
| meter | meters | meter_id, customer_type, tariff, electric_heating, connection_year, years_connected?, district |
| reading | readings | meter_id, interval_start, interval_minutes, received_at, energy, energy_unit |
| customer_profile | customer_profiles | customer_id, avg_daily_kwh, night_share, seasonality, weekend_ratio, stability, annual_charge_uah, avg_price_uah_kwh, voltage_dev_mean, loss_index_mean, tariff, meter_type, district, connection_year, churned? |
| customer_event | customer_events | customer_id, event_at, event_type |
| equipment | equipment | equipment_id, cohort, equipment_type, voltage_class, region, install_year, last_overhaul_year, outdoor |
| equipment_observation | equipment_observations | equipment_id, role, load_mean, load_std, load_stability, load_weekend_ratio, temp_rise_mean, temp_rise_std, temp_rise_median, pd_mean, pd_std, pd_stability, pd_per_load, temp_per_load, work_order_opened, failed? |
| service_case | service_cases | case_id, reactive_energy_mvarh, heat_energy_gcal, contracted_power_kw, outage_hours, service_cost_kuah? |

## Правила предметної області

- meter_id, customer_id, equipment_id і case_id належать до окремих систем ключів. Читання початкових CSV перетворює abonent_id на customer_id, а object_id на equipment_id. Зв’язок між різними системами ключів вимагає явної відповідності.
- Інтервал вимірювання починається в interval_start і триває interval_minutes хвилин. energy — спожита за інтервал енергія у заявлених Wh або kWh. received_at — час надходження цієї передачі. Імпортер початкових даних відображає ts, record_ts і consumption_kwh відповідно в interval_start, received_at і energy, задає 60 хвилин та заявлену одиницю kWh.
- Час API має містити зміщення або Z. Для локального календаря та перетворення початкового часу без зміщення потрібна відома зона IANA. Неоднозначні години переходу на зимовий час потребують явного зміщення. Перевірка існування зони та календарної дати є обов’язком імпортера.
- Набір може містити один тип даних. Довідникові записи можуть надійти після вимірювань у тому самому файлі. Брак таблиці для конкретного аналізу діагностує відповідна операція.
- Зберігаються сирі ідентифікатори, категорії, заявлені одиниці та всі повторні передачі. Очищення формує окремий результат. Якщо останні передачі мають однаковий час і різні значення, дедуплікація повідомляє про конфлікт.
- failed потрібне для training і заборонене для prediction. work_order_opened зберігається для аудиту витоку. service_cost_kuah вимірюється в тисячах гривень і потрібне для навчання моделі вартості. Для планування потрібна надана або спрогнозована вартість. case_id для історичного файлу без ідентифікаторів утворюється зі стабільного ключа джерела та порядкового номера рядка даних від 1.
- Початкові 0/1 для логічних колонок адаптер перетворює на false/true. Вихідні атрибути обладнання, повторені у train/test, звіряються з реєстром. Параметри алгоритмів (пороги, бюджет годин бригад і модель нечітких правил) належать до відповідних операцій.

## HTTP і перевірка

Після повного запису таблиць сервер публікує набір і повертає HTTP 201, dataset_id і counts за типами. У разі помилки частковий набір недоступний. Синтаксис та порядок рядків — 400, тип вмісту — 415, порушення схеми — 422. Помилки мають code та message. Для NDJSON line рахується від 1 включно із заголовком, для JSON path є JSON Pointer, наприклад /records/0/energy. Перевірка прикладів повинна давати 8 предметних записів, із них 2 reading. Після окремої дедуплікації має залишитися показ 1.45 kWh.

## Дедуплікація вимірювань

`GET /v1/datasets/{dataset_id}/readings/deduplicated` повертає файл Parquet зі схемою таблиці `readings`. Для кожної пари `meter_id` і `interval_start` залишається запис із найбільшим `received_at`. Результат упорядковано за `meter_id` та `interval_start`. Операція синхронна й сортує всю таблицю `readings` у пам’яті. Сирі передачі зберігаються в імпортованому наборі.

Якщо кілька передач мають однаковий максимальний `received_at`, однакові записи згортаються в один. Різні `interval_minutes`, `energy` або `energy_unit` у таких передачах дають HTTP 409 з кодом `reading_conflict` і полями `meter_id`, `interval_start`, `received_at`. Час порівнюється в UTC, а значення й одиниці енергії зберігаються як у джерелі.

Невідомий `dataset_id` дає HTTP 404 з кодом `dataset_not_found`. Набір без таблиці `readings` дає HTTP 422 з кодом `readings_missing`.

## Перегляд показів і підсумки споживання

Усі три маршрути повертають JSON і приймають необов’язкові фільтри `meter_id`, `start` та `end`. Межі застосовуються до `interval_start`. Початок включний, кінець виключний. Передайте дату `YYYY-MM-DD` для півночі UTC або повний час зі зміщенням чи `Z`. Якщо задано обидві межі, `end` має бути після `start`.

| Маршрут | Результат |
|---|---|
| `GET /v1/datasets/{dataset_id}/readings` | Покази в порядку `interval_start`, потім `meter_id`. `limit` за замовчуванням 100, максимум 1000. `offset` за замовчуванням 0. `total` охоплює всі відібрані покази. `next_offset` дорівнює `null` на останній сторінці. |
| `GET /v1/datasets/{dataset_id}/readings/summary` | Кількість показів і лічильників, сума, середнє арифметичне на один показ, медіана, мінімум і максимум. Без фільтрів підсумовує весь набір. |
| `GET /v1/datasets/{dataset_id}/readings/daily` | Кількість показів і статистика енергії за кожен день із показами. День визначається за початком інтервалу в UTC. |

Спочатку застосовуються фільтри за лічильником і часом, потім залишається остання передача для кожного лічильника й інтервалу. Ват-години перетворюються на кВт·год. У підсумок входить уся енергія кожного відібраного інтервалу.

Після дедуплікації можна відфільтрувати окремі покази за числовим полем `filter_field`. Типове поле `energy_kwh` приймає скінченні числа у кВт·год, а `interval_minutes` приймає цілі межі у хвилинах. Оператори `gt` і `lt` виключають межі, `gte` і `lte` включають їх, `eq` перевіряє точну рівність. Показ має задовольняти всі задані умови. Наприклад, `gte=1&lte=2` охоплює значення від 1 до 2 кВт·год включно. Поділ на сторінки та підсумки за період або за днями виконуються після цього фільтрування.

Для порожньої вибірки список показів і список днів порожні. У зведенні кількості та `total_kwh` дорівнюють 0, а середнє, медіана, мінімум і максимум дорівнюють `null`. Конфлікт передач у вибірці повертає `409 reading_conflict`. Некоректні параметри дають `422 validation_error`, а сума поза числовим діапазоном дає `422 readings_numeric_range`. Коди для відсутнього набору чи таблиці показів такі самі, як для дедуплікації.

## Якість вимірювань

`GET /v1/datasets/{dataset_id}/readings/quality` повертає JSON-звіт про якість показів. Звіт використовує дедупліковані покази та зберігає в `counts` кількість сирих і дедуплікованих рядків, вилучених повторів і лічильників із показами. Конфлікт останніх передач повертає ту саму помилку `409 reading_conflict`, що й завантаження Parquet.

| Параметр | За замовчуванням | Правило |
|---|---|---|
| `window_end` | Найпізніший `interval_start` набору | Кінець спостереження зі зміщенням або `Z`. Має бути не раніше за найпізніший `interval_start`. |
| `silence_hours` | `48` | Лічильник потрапляє до `silent_meters`, якщо від початку останнього інтервалу до `window_end` минуло більше годин. |
| `frozen_ratio` | `0.65` | Лічильник потрапляє до `frozen_meters`, якщо частка різних значень енергії після перетворення Wh у kWh менша за поріг від 0 до 1. |
| `unit_ratio` | `100` | Лічильник потрапляє до `unit_check.suspected_meters`, якщо його медіана погодинної енергії, поділена на медіану всіх погодинних показів того самого типу споживача, перевищує поріг. |

Перевірки тиші й повторюваності охоплюють лічильники, для яких є хоча б один показ. Пороги мають бути скінченними й невід’ємними. Некоректний параметр дає HTTP 422 з кодом `validation_error` і `path` із назвою параметра.

Перевірка масштабу використовує 60-хвилинні інтервали, переводить заявлені Wh у kWh і зіставляє `meter_id` з реєстром `meters` за точним збігом. `unit_check` дорівнює `null`, якщо реєстру немає. Інакше `evaluated_meters` показує кількість лічильників із погодинними показами, однозначним `customer_type` і додатною медіаною групи. Підозріле відношення поза діапазоном скінченних `float64` повертається як `null` у полі `ratio`. Звіт діагностує аномалії без коригування сирих даних.

## Регресія споживання домогосподарств

`GET /v1/datasets/{dataset_id}/readings/household-regression` навчає лінійну модель добового споживання. Для кожного домогосподарства ціль дорівнює середньому показу за 60-хвилинний інтервал, помноженому на 24. Ознаки моделі — `electric_heating` і `dual_zone` (двозонний тариф). Відповідь містить `intercept` і `coefficients` у kWh на добу, навчальний `r_squared`, кількість лічильників `meter_count` і застосовані параметри.

Маршрут приймає ті самі параметри `window_end`, `silence_hours`, `frozen_ratio` та `unit_ratio`, що й звіт якості. Він дедуплікує покази, зіставляє погодинні рядки з реєстром за `meter_id` і використовує домогосподарства з тарифами `single` або `dual_zone`. Для моделі заявлені Wh переводяться у kWh. Заявлені kWh для лічильників, позначених перевіркою масштабу, діляться на 1000. `rescaled_meter_ids` містить такі лічильники серед використаних у моделі. Замовклі лічильники виключаються за часом останнього погодинного показу, а завмерлі — за часткою різних погодинних значень після перерахунку. Сирі дані зберігаються.

Для оцінки двох коефіцієнтів потрібні щонайменше три придатні домогосподарства й незалежна варіація обох ознак. Брак даних або залежні ознаки дають `422 insufficient_regression_data`. Окремі коди `422` позначають відсутній реєстр (`meters_missing`), відсутні погодинні покази (`hourly_readings_missing`), суперечливі атрибути реєстру (`meter_registry_conflict`) і вихід чисел за підтримуваний діапазон (`regression_numeric_range`). Невідомий набір і конфлікт передач дають ті самі `404` і `409`, що й звіт якості.

## Сегментація споживачів

`GET /v1/datasets/{dataset_id}/customers/segmentation` сегментує споживачів за таблицею `customer_profiles`. Параметр `k` — ціле число від 2 до 8, за замовчуванням `4`. Потрібні унікальні `customer_id`, додатні `avg_daily_kwh`, щонайменше `k + 1` профілів і `k` різних векторів ознак.

- Для кластеризації логарифмується `avg_daily_kwh`, після чого п’ять ознак споживання стандартизуються. `kmeans_candidates` містить інерцію й силует для доступних значень `k` від 2 до 8. Для k-середніх використовуються 10 ініціалізацій і `random_state=0`. Повторний запит із тими самими профілями й `k` дає той самий поділ за тих самих версій бібліотек. Останні знаки інерції можуть різнитися через паралельне підсумовування.
- `pca` містить власні значення, пояснену дисперсію, підсумок за критерієм Кайзера (`eigenvalue > 1`) і навантаження `PC1` та `PC2`. PCA використовує дев’ять стандартизованих числових ознак без логарифмування.
- `ward_cut_gaps` містить різниці висот сусідніх злиттів для доступних `k` від 3 до 6. `adjusted_rand_index` і `contingency` порівнюють обидва поділи. У `contingency.counts` рядки відповідають `segment_ids`, а стовпці — `ward_ids`. K-середніх нумерує сегменти від 0, метод Варда — від 1 і може повернути менше ніж `k` груп за однакової висоти злиття.
- `assignments` містить обидві мітки кожного споживача. `profiles` і `baseline` подають кількість споживачів, середні значення п’яти ознак у початкових одиницях, частку `IND_1985` та частку `churned` серед відомих значень. Частка `churned` дорівнює `null`, якщо таких значень немає.

Невідомий набір дає `404 dataset_not_found`. Коди `422` пояснюють некоректне `k` (`validation_error`), відсутню таблицю (`customer_profiles_missing`), повторний ключ (`duplicate_customer_id`), недодатне споживання (`nonpositive_avg_daily_kwh`), брак даних для поділу (`insufficient_segmentation_data`) або вихід за числовий діапазон (`segmentation_numeric_range`). Для методу Варда потрібна пам’ять, що зростає квадратично з кількістю профілів.

## Карта Кохонена

`GET /v1/datasets/{dataset_id}/customers/som` будує карти Кохонена за таблицею `customer_profiles`. Використовуються ті самі ознаки, перевірки й параметр `k`, що й у сегментації. Профілі впорядковуються за `customer_id` до навчання. Мітки `segment_id` у відповіді відповідають k-середніх із маршруту сегментації для того самого `k`.

За функцією `train_som` із ноутбука навчаються дві карти 15×15 з `sigma=1.5` і `sigma=0.5`. Кожна використовує PCA-ініціалізацію, швидкість навчання `0.5`, зерно `0` і 20 000 ітерацій із випадковим порядком подачі профілів. У `maps` для кожного радіуса повертаються `topographic_error`, нормована `distance_map` та `assignments`. Топографічна помилка — частка профілів, у яких два найближчі нейрони не є сусідами. Координати `x` і `y` — індекси нейрона-переможця від 0 до 14. У матриці відстань для вузла лежить у `distance_map[x][y]`.

Операція синхронно навчає обидві карти. Крім спільних помилок підготовки даних і сегментації, вихід обчислень SOM за числовий діапазон дає `422 som_numeric_range`.

## Асоціативні правила переходу до іншого постачальника

`GET /v1/datasets/{dataset_id}/customers/churn-rules` шукає асоціативні правила переходу за таблицями `customer_profiles` і `customer_events`. Без `min_support` відповідь містить звіти для підтримки `0.05` і `0.10`. Параметр `min_support` у діапазоні `(0, 1]` вибирає один поріг. Параметр `min_confidence` у діапазоні `[0, 1]` задає мінімальну достовірність, за замовчуванням `0.30`.

Події зіставляються з профілями за `customer_id`. Для кожного абонента враховується наявність кожного типу події. Типи `churn` і `churned` виключаються, а наслідок береться з поля `customer_profiles.churned`. Підтримку та базову частку переходів обчислюють серед усіх абонентів із відомою міткою, включно з тими, хто не має подій. `customer_count` охоплює всі профілі, `labeled_customer_count` — профілі з відомою міткою.

Apriori та `association_rules` формують правила з єдиним наслідком `churned`. Кожен звіт містить поріг `min_support`, кількість `rule_count` і список `rules` зі значеннями `support`, `confidence`, `lift` та умовами `antecedents`. Підтримка — частка абонентів з умовами й наслідком, достовірність — частка переходів серед абонентів з умовами, ліфт — відношення достовірності до базової частки переходів `churn_rate`. Правила впорядковано за спаданням ліфту, а однакові ліфти — за назвами умов. Застосовується вся історія імпортованих подій.

Для відомих міток без жодного правила повертається `200` із порожнім списком. Невідомий набір дає `404 dataset_not_found`. Некоректні параметри (`validation_error`), відсутня таблиця профілів (`customer_profiles_missing`), відсутня таблиця подій (`customer_events_missing`), дублікати профілів (`duplicate_customer_id`) і відсутність відомих міток (`churn_labels_missing`) дають `422`.

## Перевірки T-1, T-2 і T-3

`GET /v1/datasets/{dataset_id}/customers/pitfalls` перевіряє три статистичні пастки за таблицею `customer_profiles`. Відповідь містить статистику, критерії та поле `detected` для кожної перевірки.

- **T‑1.** Кореляція Пірсона між `voltage_dev_mean` і `loss_index_mean` має модуль понад `0.20` у всій базі та нижче `0.10` у кожному `district`.
- **T‑2.** Відношення середньої `seasonality` для `IND_1985` до середньої для решти лічильників виходить за межі `[0.8, 1.2]`.
- **T‑3.** Кореляції Пірсона між `avg_price_uah_kwh` і `churned` мають протилежні знаки у двох групах. Перша група охоплює 30% профілів із найбільшим `annual_charge_uah`, з округленням кількості вниз. За однакової оплати порядок визначає `customer_id`. Друга група охоплює решту. Кореляції рахуються серед відомих `churned` у кожній групі.

Невизначені статистики повертаються як `null`. Це може статися через порожню групу, сталу ознаку, недостатню кількість відомих міток або нульовий знаменник. Якщо потрібна статистика невизначена, відповідний `detected` також дорівнює `null`. Відсутня таблиця профілів або повторний `customer_id` дають `422`, а невідомий набір — `404`.

## Аудит даних обладнання

`GET /v1/datasets/{dataset_id}/equipment/audit` виконує перевірки M‑1, M‑2 і M‑3. Маршрут зіставляє `equipment_observations` з `equipment` за `equipment_id`, розділяє спостереження за `role` і повертає кількість обладнання, спостережень та частку відмов серед `training`.

- **M‑1.** Для кожної числової або логічної ознаки, включно з `work_order_opened`, обчислюється ROC AUC відносно `failed`. Скоригований бал дорівнює `max(AUC, 1 - AUC)`. Ознаки з балом строго понад `0.90` потрапляють до `flagged_columns`. `scores` упорядковано за спаданням скоригованого бала, а за рівності — за назвою ознаки.
- **M‑2.** Покриття — частка унікальних об’єктів `history`, присутніх у `training`. Менше `0.90` позначає зміщену вибірку. Звіт повертає середній `install_year` охопленої та неохопленої частин когорти й кількість навчальних об’єктів поза `history`.
- **M‑3.** Перевірка зсуву середнього електричного навантаження. Поле `m3.feature` має значення `load_mean`. Зсув зі знаком дорівнює середньому `load_mean` у `prediction` мінус середнє у `training`, поділеному на вибіркове стандартне відхилення `load_mean` у `training`. `detected` спрацьовує, якщо модуль зсуву строго понад `0.50`.

Для невизначених статистик і відповідних прапорців `detected` повертається `null`. Наприклад, ROC AUC потребує обох класів, а M‑3 — двох вибірок і ненульового навчального відхилення. Відсутня таблиця (`equipment_missing` або `equipment_observations_missing`), повторний ключ у реєстрі (`duplicate_equipment_id`) і спостереження без відповідного запису реєстру (`unknown_equipment_id`) дають `422`. Невідомий набір дає `404 dataset_not_found`.

## Оцінювання моделі відмов обладнання

`GET /v1/datasets/{dataset_id}/equipment/model-evaluation` навчає й оцінює модель, задану параметром `model`. За замовчуванням це `perceptron`. Підтримувані моделі наведено нижче.

| `model` | Налаштування |
|---|---|
| `perceptron` | 32 нейрони в прихованому шарі, за замовчуванням `alpha=1.0`, до 1 000 ітерацій, `random_state=0` |
| `decision_tree` | Максимальна глибина 5, `random_state=0` |
| `svm` | SVC з калібруванням імовірностей, до 5 згорток залежно від кількості спостережень меншого класу |
| `knn` | 25 сусідів або всі навчальні спостереження, якщо їх менше |
| `naive_bayes` | GaussianNB |

Спостереження `training` впорядковуються за `equipment_id` і діляться на навчальну та валідаційну частини стратифіковано за `failed`. Частка валідації — 25%, `random_state=0`. На навчальній частині визначаються one-hot колонки для `equipment_type`, `voltage_class` і `region`, ознаки зі скоригованим ROC AUC понад 0.90 та параметри `StandardScaler`. `work_order_opened` виключається завжди. Невідомі у навчанні категорії валідації кодуються нулями у відповідній групі колонок. Звіт повертає `feature_columns`, `excluded_features` і метрики `pr_auc` (average precision), `roc_auc`, `failure_rate` та `count` для `training` і `validation`.

Для перцептрона можна задати одне скінченне `alpha ≥ 0`. У відповіді для цієї моделі є застосоване `alpha`. `pr_auc_gap` для вибраної моделі дорівнює `training.pr_auc − validation.pr_auc`. Щоб перевірити вплив регуляризації на перенавчання, надішліть окремі запити для `0.0001`, `0.001`, `0.01`, `0.1` і `1.0`. Поділ даних і підготовка ознак для цих запитів однакові.

Для поділу потрібен один рядок `training` на об’єкт і обидва класи в обох частинах. Повторний навчальний об’єкт дає `422 duplicate_training_equipment`, брак даних — `422 insufficient_failure_data`, брак придатних ознак — `422 no_model_features`, вихід за числовий діапазон — `422 model_numeric_range`. Невідоме значення `model` дає `422 validation_error` із шляхом `/model`. Некоректне чи повторне `alpha`, а також `alpha` для іншої моделі дають `422 validation_error` із шляхом `/alpha`. Також діють перевірки таблиць і ключів з аудиту обладнання.

## Пріоритет перевірки лічильника

`GET /v1/datasets/{dataset_id}/readings/inspection-priority` приймає один непорожній `meter_id` і необов’язковий `window_end`. Якщо час пропущено, використовується найпізніший початок інтервалу в усьому наборі. Маршрут дедуплікує покази вибраного лічильника й порівнює енергію в kWh.

| Показник | Як обчислюється |
|---|---|
| `hours_since_last_reading` | Години між початком останнього інтервалу лічильника та `window_end`. |
| `unique_ratio` | Кількість різних значень енергії, поділена на кількість показів після дедуплікації. |
| `repetition_ratio` | `1 − unique_ratio`. Повторні передачі вже вилучено. |
| `priority_score` | Евристичний бал Мамдані на шкалі 0–100 для порядку ручної перевірки. |
| `rule_strengths` | Сили правил планової (`routine`) і першочергової (`escalate`) перевірки. |

Ступені належності до підвищеної затримки й повторюваності дорівнюють 0.5 на стандартних порогах звіту якості: 48 годин і 35% повторюваних значень. Затримки від 96 годин однаково впливають на бал. Правило `routine` спрацьовує, коли обидва показники низькі. Для `escalate` достатньо одного підвищеного показника. Підсумок обчислюється за центроїдом об’єднаних нечітких множин. Бал використовує фіксовані правила для розстановки пріоритетів ручної перевірки.

Невідомий набір або лічильник без показів у наявній таблиці дає 404. Конфлікт останніх передач вибраного лічильника дає `409 reading_conflict`. Набір без таблиці показів, відсутній чи повторний `meter_id` або некоректний `window_end` дають 422.

`GET /v1/readings/inspection-priority/surface` повертає сітку 21 × 21 без імпорту даних. У матриці `priority_scores` рядки відповідають осі `repetition_ratio` від 0 до 1, стовпці — осі `hours_since_last_reading` від 0 до 96.

## Нейро-нечітка модель вартості з КП

Друга частина КП використовує `service_cases`. Входи — `reactive_energy_mvarh`, `heat_energy_gcal`, `contracted_power_kw` і `outage_hours`, ціль — `service_cost_kuah`. Випадки з відомою вартістю діляться на навчальну і тестову частини 75/25 із `random_state=0`. Для стабільного поділу рядки впорядковуються за `case_id`. Ідентифікатори виду `sample:<номер>` впорядковуються за номером після назви джерела. Масштаби всіх ознак і цілі визначаються за мінімумом і максимумом навчальної частини.

- `GET /v1/datasets/{dataset_id}/service-cases/subtractive-clustering` обчислює `rule_count` для одного додатного скінченного `radius` на нормованих навчальних входах і цілі. Типовий радіус — `0.5`, пороги відбору центрів — `0.5` і `0.15`, як у ноутбуці.
- `GET /v1/datasets/{dataset_id}/service-cases/cost-model` будує модель Сугено з однією кількістю правил c‑means. Параметр `rules` приймає значення від 2 до 6, типове значення — 3. `baseline`, `initial` і `tuned` містять RMSE прогнозу середнім, початкової та налаштованої моделі на обох частинах і розрив `test − train`. Усі RMSE вимірюються в тис. грн. Налаштування L‑BFGS‑B використовує навчальну частину. `optimization` повертає статус збіжності та кількість ітерацій. `predictions` містить прогноз налаштованої моделі для кожного `case_id` без наданої вартості.

Відсутня таблиця `service_cases`, повторний `case_id`, замало випадків із вартістю, стала навчальна ціль або числа поза діапазоном обчислень дають `422`. Некоректний чи повторний параметр дає `422 validation_error` зі шляхом `/radius` або `/rules`. Невідомий набір дає `404 dataset_not_found`.
